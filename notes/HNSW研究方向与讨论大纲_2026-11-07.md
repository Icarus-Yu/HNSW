## 二、研究对象与问题边界

HNSW（Hierarchical Navigable Small World）是一类用于近似最近邻检索的分层图索引。查询时，算法从图中的入口出发，通过比较距离逐步靠近目标区域，并维护候选与结果集合。

本课题拟关注以下查询过程：访问邻接表、检查节点访问状态、读取候选向量、计算距离、维护候选集合、判断是否继续搜索。

相应开销可能包括距离计算、随机数据访问、候选队列维护、分支判断及并行执行开销。不能在测量前假定所有数据集都受缓存缺失限制。

建议先限定为：一个 HNSW 实现、一个主要 CPU 平台、以静态数据上的查询为核心、一项主要优化。索引构建时间与内存开销作为代价指标，不同时承担完整向量数据库研发。

## 四、方向 A：HNSW 查询访存与执行优化（推荐候选）

### 4.1 核心研究问题

在相同召回率要求下，能否通过改善数据访问与搜索执行组织，降低 CPU 上 HNSW 的查询延迟？收益在哪些向量维度、数据规模和搜索参数下成立？

### 4.2 问题直觉

HNSW 查询需要沿图访问分散的数据。单次访问的计算未必复杂，但下一步可能依赖尚未读取到的数据。即使 CPU 有较强计算能力，也可能因为数据访问依赖而无法充分利用。

本方向既可以研究“数据放在哪里”，也可以研究“何时读取、何时处理”。因此不局限于节点重排，但仍围绕同一个数据访问问题。

### 4.3 可考虑的手段

1. 布局调整：改善邻接表、向量和辅助状态的组织方式。
2. 访问组织：减少重复或无效访问，调整已确定邻居的处理过程。
3. 预取协同：研究预取目标、距离和时机与实际计算的配合。
4. 延迟隐藏：让相互独立的数据请求或计算重叠。
5. 查询交错：在适合的负载下交错处理多个查询，但必须区分单查询延迟、吞吐和等待时间。

以上仅为候选手段。应先定位一项主要瓶颈，再选择一个核心方法，避免将全部优化打包成难以解释的系统。

### 4.4 创新边界与风险

hnswlib 已经包含预取实现，因此“加入预取”本身不能直接作为创新。图重排也有已有研究，需要明确与现有方法的差异。

若修改改变邻居展开顺序或候选更新时机，可能改变搜索路径与结果；不能预设查询结果完全不变。即使仅改变布局，也需要验证内部编号映射、边关系和结果标签的正确性。

可探索的贡献形式包括：针对明确负载提出执行组织改进、建立可解释的适用条件、分析方法收益与额外开销。是否具有足够新颖性和工作量，需要与导师确认。

### 4.5 暂拟题目

- 面向 CPU 的 HNSW 查询访存与执行优化研究
- HNSW 图近邻搜索的访存行为分析与优化

题目暂不绑定“自适应”“新型”等尚未形成的方法特征。

### 4.6 近期核心参考与阅读安排

当前选定 [VSAG：PVLDB 2025 正式 PDF](../papers/cache/2025_VSAG_Optimized_Search_Framework_for_Graph_Based_ANNS_PVLDB.pdf) 为方向 A 的近期核心参考，重点阅读第 3 节的预取、访问组织和部分冗余布局；[官方论文](https://www.vldb.org/pvldb/vol18/p5017-cheng.pdf) 与 [作者代码](https://github.com/antgroup/vsag) 可用于后续对照。

选用依据是研究对象与 CPU 图检索访存问题直接相近，且具备正式发表版本和公开实现。2022 图重排保留为基础参考，KBest 作为 CPU 平台相关对照。VSAG 同时包含量化及调参，核心参考不等于全面复现其系统；当前不恢复量化为独立候选方向。

VSAG 已覆盖有效邻居分组、预取步长与深度、冗余布局等设计，不能把相同通用思路直接声称为新贡献。后续需固定代码版本与数据表示，区分访存改变和搜索工作量、精度及调参的影响，再确定可研究问题。

新增的图检索评测、概率路由、HNSW 插入顺序与召回材料，用于补齐实验设计和相关工作边界。选择理由及阅读层次见 [Cache 专题第 8 节](HNSW_Cache优化方向与实验条件_2026-11-08.md#8-论文阅读材料与版本)。

## 五、方向 B：多核与 NUMA（条件性候选）

### 5.1 核心研究问题

在真实多节点 NUMA 服务器上，怎样安排 HNSW 索引数据、工作线程和查询任务，才能减少跨节点访问与资源失衡，在相同检索质量和可比资源条件下提高并发查询吞吐、改善响应延迟？

### 5.2 优化对象与初期边界

主要研究数据分配、索引副本、线程组、查询队列和任务分发。先限定一个静态 HNSW 索引、只读查询、一个查询由一个线程执行，多个查询并发；保留原有图结构、距离计算和搜索参数作为起步对照。

这与将一个 HNSW 查询拆到多个节点合作执行不同。后者涉及搜索依赖、候选同步和结果合并，初期不同时承担。

### 5.3 从哪里开始

1. 确认 NUMA 节点、核心、节点内存与可控制的线程和页面放置条件。
2. 比较单节点及跨节点线程运行，测试共享索引集中分配和交错分配等基线；区分核心数量和放置位置。
3. 建立每节点完整本地副本的对照，核对真实页面位置，并报告副本和线程私有状态的空间成本。
4. 结合证据，在有限预算的部分复制或局部性与负载协调中选一项主要问题。仅绑核、调整分配参数或复制索引，不自动构成新的研究方法。
5. 比较 QPS、包含排队的响应延迟、纯搜索耗时、召回率、实际放置和额外成本；说明收益与退化条件。

详细候选方法、文献边界与实施位置见 [NUMA 专题记录](HNSW_NUMA优化方向与论文依据_2026-11-08.md)。

### 5.4 已有研究与选择前提

Quake 已研究分区向量索引中的 NUMA 数据放置与查询内并行；2026 年 CCD-Level 工作已研究 HNSW 多表查询的缓存域映射、负载适应和任务窃取。二者分别属于不同索引和不同拓扑尺度，不能直接作为 HNSW NUMA 复制方案已解决或尚无人研究的证明。

已有工作也在近内存计算中采用 HNSW 热点数据复制。因此，具体创新性仍需方法对照与目标平台实验，当前学校服务器条件未确认，尚未运行 HNSW NUMA 实验。

### 5.5 暂拟题目

- 面向 NUMA 架构的 HNSW 并发查询执行优化研究
- 有限内存预算下的 HNSW NUMA 数据放置与并发查询优化研究

第二个题目只适合后续确实选择预算约束问题的情况；当前均非最终题目。

## 八、研究评价原则与预期成果

### 8.1 评价原则

主要在相同召回率目标下比较查询性能，不能仅固定搜索参数，也不能用牺牲召回率换取的速度变化证明优化有效。

| 维度 | 主要指标与注意点 |
| --- | --- |
| 检索质量 | Recall@k；使用一致距离度量与精确近邻真值 |
| 单查询性能 | 延迟分布，如 P50/P95；记录测量方式 |
| 吞吐 | 固定线程数与负载口径下的 QPS |
| 系统代价 | 索引空间、峰值内存、构建或预处理时间 |
| 机制证据 | 热点、距离计算次数、可用硬件事件；结合多项证据解释 |
| 稳定性 | 重复测量、结果波动、后台负载与实验条件 |

perf 是辅助定位和解释性能的工具，不是研究方向本身。单个缓存事件不能独立证明内存瓶颈，不同 CPU 的事件含义与可用性需要核对。

同一台机器上比较原始版与改进版；不同机器分别报告收益。跨平台实验用于讨论可迁移性，不直接将两台机器的绝对运行时间作为算法改进证据。

### 8.2 预期成果

- 明确的瓶颈分析与相关工作对照。
- 一个核心优化方法及可审查的实现修改。
- 基线、对照与消融实验，以及原始结果和复现说明。
- 对收益、代价、适用条件和失败情况的解释。
- 完整毕业论文；应用演示作为可选补充。

目前不预设加速比例，不将复现结果或设想写成独立创新。若只有参数调节，应据实界定贡献；复现、分析与改进的最低要求需与导师确认。

## 九、RAG 与 Agent 的位置

| 层次 | 负责什么 | 在本课题中的角色 |

建议将主要精力用于论文，可暂按 80% 研究、20% Agent 学习安排。配套学习链路包括 Python 与模型接口、文档入库、固定流程 RAG、工具调用循环、状态与错误处理、接口服务及日志评测。
