## 2. NUMA 是什么，哪些概念需要区分

NUMA 是 Non-Uniform Memory Access，即非一致内存访问。CPU 访问同一台机器内不同位置的主内存，延迟和可用带宽可能不同。非一致描述访问代价，不表示内存内容不一致。

| 概念 | 含义 | 不能直接等同于什么 |
| --- | --- | --- |
| CPU 核心 | 执行指令的物理计算核心 | 一个 NUMA 节点 |
| 逻辑线程 | 操作系统可调度的逻辑处理器上下文 | 一份完整独立物理核心资源 |
| CPU 插槽 | 安装处理器封装的位置 | 固定数量的 NUMA 节点 |
| NUMA 节点 | 操作系统呈现的内存访问拓扑单元 | 一台独立联网服务器 |
| 本地、远端内存 | 相对某个执行核心或节点而言的内存位置 | SSD 访问或网络远程文件 |
| CCD / 缓存共享域 | 核心芯粒或共享缓存的拓扑概念 | 必然与 NUMA 内存节点一一对应 |

单插槽也可能包含多个 NUMA 节点；具体以硬件、固件和操作系统实际暴露的拓扑为准。线程能访问远端内存，但可能经过额外互连路径。软件需要同时考虑线程调度、内存页面分配和数据结构组织。[微软架构说明](https://learn.microsoft.com/en-us/windows/win32/procthread/numa-support)

申请内存和页面实际分配不是同一步。在常见本地分配策略下，首次实际触及页面的线程位置会影响页面落点，还受显式策略、回退和迁移等机制影响。线程绑定不等于数据已经正确放置。[Linux 内存策略](https://docs.kernel.org/admin-guide/mm/numa_memory_policy.html)

## 3. 为什么 HNSW 会涉及 NUMA

HNSW 查询沿图读取邻接信息、访问标记和向量。访问位置由搜索过程不断决定，可能在不同内存区域之间跳转。

以下只是说明问题的假设，不是学校服务器配置：两个 NUMA 节点各有一组核心和 64 GB 本地内存，一份静态索引为 40 GB。

| 数据与执行安排 | 潜在收益 | 需要承担或验证的问题 |
| --- | --- | --- |
| 索引主要位于节点 0，线程分布于两边 | 空间占用较低 | 节点 1 的线程可能频繁跨节点读取 |
| 索引页面分布在两个节点 | 利用多个内存控制器的容量和带宽 | 单个查询仍可能同时访问本地、远端页面 |
| 每个节点拥有完整本地副本 | 查询可使用所在节点的数据 | 索引空间约翻倍，初始化与维护成本增加 |
| 只复制部分数据 | 额外空间可控 | 副本选择、定位、查询分布变化带来新问题 |

本地性不是唯一目标。只用本地数据可能使某节点过载、另一节点空闲；交错分配虽增加部分远端访问，却可能改善总带宽利用。需要在局部性、负载均衡、带宽和额外内存之间权衡。

## 4. 四类候选工作

### 4.1 线程与内存放置的系统分析

先比较单节点、跨节点线程布局，以及集中分配、交错分配等页面策略；记录初始化方式、实际页面位置、线程数量和吞吐变化。

需要回答：HNSW 是否在目标服务器上出现明显 NUMA 扩展性问题？原因更接近远端访问延迟、带宽失衡、共享状态竞争，还是其他因素？

该部分应作为基线与瓶颈分析。仅改变系统启动参数或比较几组配置属于实验分析与调优，不能自动形成独立方法贡献；最低要求需与导师确认。

### 4.2 完整索引复制

每个 NUMA 节点的本地内存保存相同静态索引，节点内线程组使用本地副本，查询由一个节点完成。

主要工作包括：建立真实的本地数据副本、控制初始化和页面放置、建立线程组与查询分配、检查结果与记录空间代价。多个虚拟映射或多个对象名不自动意味着存在不同节点上的物理副本。

核心评价问题是额外内存能换来多少吞吐、延迟和稳定性收益，以及哪些索引规模能容纳副本。完整复制是重要对照，但复制本身是已有系统思路。动态更新会增加副本维护问题，当前可先限定只读索引。

### 4.3 有限内存预算下的选择性复制

考虑只复制部分邻接信息、向量、层级数据或其他访问对象。需要统计访问行为、定义选择策略、修改读路径、维护编号对应关系，并提供未命中本地副本时的回退方式。

| 关键问题 | 需要调查的内容 |
| --- | --- |
| 复制什么 | 邻接信息和向量的收益是否不同？ |
| 选择标准 | 访问频率是否反映真正昂贵的远端读取？ |
| 内存预算 | 不同额外空间下收益如何变化？ |
| 查询变化 | 统计查询与独立测试查询之间是否仍适用？ |
| 读路径成本 | 额外查找和映射能否覆盖节省的访问代价？ |

最热的数据可能已经留在 CPU 缓存中，因此不能直接按访问次数认定复制价值。该路线是候选调查方向，尚未确认其具体设计的创新性或预期收益。

### 4.4 局部性与负载共同驱动的查询调度

每个节点维护本地队列与线程组，优先使用合适的本地数据；在等待或负载过高时，决定是否把工作交给其他节点。

可以调查队列长度、等待时间、节点负载与数据副本位置的联合使用，以及节点内优先、必要时跨节点获取工作的机制。

调度应配合可解释的数据放置或副本结构。如果所有查询随机访问同一份全局索引，仅给查询指定“所属节点”不会自动产生局部性。

单个 HNSW 查询如何拆到多个节点协同执行，是另一种范围更大的选择，涉及依赖、候选同步和搜索路径，当前建议先区分于多个独立查询并发的路线。

### 4.5 关于图分区的边界

将同一张图的数据分布到不同节点后，搜索仍可能跨分区访问。不能简单丢弃跨分区边，或把每个分区的局部结果当成全局检索质量保证。若改成独立分片检索再合并，需要重新描述算法、路由与召回评价，工作范围会扩大。

### 4.6 实际从哪些位置动手

先将搜索内核与并发执行分开，按测量结果决定改动范围。以下以 hnswlib 为例，后续实验需固定提交版本。

| 位置 | 起步工作 | 需要验证的事项 |
| --- | --- | --- |
| 索引创建和加载 | 控制分配策略、初始化线程与页面首次实际触及位置 | 线程绑定后，索引页面是否确实位于目标节点；是否被迁移 |
| 工作线程组 | 绑定核心，按节点组织工作线程 | 相同核心数的放置对照，避免把增加核心的收益算成方法收益 |
| 查询分发与队列 | 维护节点队列和副本位置映射 | 排队等待、调度开销、局部性与负载是否平衡 |
| 查询辅助状态 | 检查访问标记池和线程私有缓冲的分配及复用 | 是否跨节点复用、是否存在池管理争用、额外内存有多大 |
| 索引复制 | 节点内独立初始化完整副本，或为部分复制设计本地查找与回退 | 是否为真实物理副本，是否保持图连接、标签和检索质量 |
| 搜索数据访问接口 | 仅在部分复制确有价值时修改节点数据读取 | 额外映射开销是否超过节省的远端读取代价 |

hnswlib 的 `hnswalg.h` 包含 `data_level0_memory_`、`linkLists_` 等存储及加载路径；`visited_list_pool.h` 包含访问标记缓冲和池管理。源码存在这些结构不代表已证明它们在目标机器上构成瓶颈。完整复制和线程调度可以先在执行层实现；部分复制才可能需要更深入修改节点读取路径。

源码依据：[索引与查询实现](https://github.com/nmslib/hnswlib/blob/master/hnswlib/hnswalg.h)、[访问标记池](https://github.com/nmslib/hnswlib/blob/master/hnswlib/visited_list_pool.h)、[Linux NUMA 内存策略](https://docs.kernel.org/admin-guide/mm/numa_memory_policy.html)。

## 5. 已核实的近期论文依据

近期以 2024–2026 年为筛选范围。版本、来源、页数和校验信息统一记录在 [论文目录](../papers/README.md) 与 [catalog.json](../papers/catalog.json)。以下区分直接相关、拓扑调度相关与相邻研究，不将它们全部称为 HNSW 专用 NUMA 优化论文。

### N1. Quake: Adaptive Indexing for Vector Search

- 作者：Jason Mohoney、Devesh Sarda、Mengze Tang 等。
- 发表：OSDI 2025，153–169 页。
- 本地文件：[正式会议 PDF](../papers/numa/2025_Quake_Adaptive_Indexing_for_Vector_Search.pdf)，包括会议封面共 18 个 PDF 页面。
- 来源：[USENIX 正式页面](https://www.usenix.org/conference/osdi25/presentation/mohoney)、[实验代码](https://github.com/marius-team/quake/tree/osdi2025/test/experiments/osdi2025)。

与本文的关系：直接面向向量检索，将分区放到不同 NUMA 节点，并按数据位置组织工作线程和查询内并行。重点阅读正式版实现与 NUMA 扩展性实验。

边界：Quake 是分区式索引；HNSW 图遍历的后续访问动态决定，不能直接照搬其扫描任务划分。系统总体性能包含多项设计，不能把摘要中的整体加速全部归因于 NUMA，也不能套用为本课题预期收益。

### N2. CCD-Level and Load-Aware Thread Orchestration for In-Memory Vector ANNS on Multi-Core CPUs

- 作者：Yuchen Huang、Baiteng Ma、Yiping Sun 等。
- 状态：arXiv 页面标注 Accepted by ICDE 2026。
- 本地文件：[arXiv:2605.10090v1，2026-05-11](../papers/numa/2026_CCD_Level_and_Load_Aware_Thread_Orchestration_arxiv2605.10090v1.pdf)，14 页。
- 来源：[作者预印本页面](https://arxiv.org/abs/2605.10090)。

这是本次整理时新增的近期相关材料。它研究多芯粒 CPU 上的任务映射、缓存局部性与负载感知调度，覆盖查询间并行的 HNSW 和查询内并行的 IVF。

与本文的关系：直接说明 HNSW 并发执行、缓存域和负载调度已有较近研究，后续候选方案必须与之比较。

边界：CCD 及缓存共享域不等于 NUMA 内存节点。论文放入 numa 分类是因为它属于拓扑感知并发调度的相邻问题；不能据此声称已经解决普通多插槽 HNSW NUMA 放置。本地下载的是作者预印本，接收状态按作者页面标注，尚未另行取得出版社最终排版版本。

### N3. UDON: A case for offloading to general purpose compute on CXL memory

- 作者：Jon Hermes、Josh Minor、Minjun Wu、Adarsh Patil、Eric Van Hensbergen。
- 状态：arXiv 页面说明 Presented at HCDS 2024。
- 本地文件：[arXiv:2404.02868v1，2024-04-03](../papers/numa/2024_UDON_Offloading_to_General_Purpose_Compute_on_CXL_Memory_arxiv2404.02868v1.pdf)，5 页。
- 来源：[作者预印本页面](https://arxiv.org/abs/2404.02868)。

与本文的关系：使用双路 ARM NUMA 系统模拟 CXL 场景，涉及 HNSW 索引与查询的内存敏感性和计算卸载原型，可帮助理解“让计算靠近数据”。

边界：主要问题是 CXL 近内存计算，并非普通多路服务器上的通用 NUMA 优化。其硬件设置、基线与收益不能直接迁移到本课题。

### 5.2 当前研究进展与新增边界核对（2026-11-09）

- Quake 已将分区与 NUMA 节点、执行线程结合，并在其 NUMA 扩展性实验中使用 MSTuring100M、90% 召回目标和最高 64 个工作线程。这是分区扫描的查询内并行，不能当成 HNSW 查询间并发的直接收益依据。[作者原文第 6、7.5 节](https://arxiv.org/html/2506.03437v2)
- CCD-Level 工作已经把 HNSW 表映射到缓存共享域，依据访问流量调整映射，并采用优先同域的任务窃取。其 HNSW 负载包含同机多张表，不能默认同样策略在单个共享大图上也有效；CCD 的缓存局部性与 NUMA 的主内存位置应分开验证。[作者原文第 IV–VIII 节](https://arxiv.org/html/2605.10090v1)
- 新增相关工作边界：[ANSMET，ISCA 2025，作者公开 PDF](https://people.iiis.tsinghua.edu.cn/~huanchen/publications/ansmet-isca25.pdf) 在第 5.3 节采用热点向量复制，并讨论 HNSW 高层节点；其研究对象是内存 rank 级近数据处理及软硬件协同，通过模拟器评估。这不是通用 CPU NUMA 软件方案，但已足以说明“复制上层热点”不能直接声称是新想法。本次仅增加在线阅读入口，尚未下载入本地论文集合。

综合这些材料，已存在数据与执行位置协同、负载适应调度和热点复制等研究。当前可调查的问题，是在具体 CPU NUMA 平台、静态 HNSW 大图及明确内存预算下，哪些数据值得复制，复制后的查找代价多大，以及什么时候跨节点分配查询更有利。这里只提出待验证问题，不声称相关工作中尚无相同方案。

## 6. 可能的实验设计

### 6.1 必须分开的两个目标

| 目标 | 执行方式 | 主要评价 |
| --- | --- | --- |
| 并发吞吐与服务延迟 | 不同查询交给不同线程 | QPS、查询延迟和排队等待 |
| 单查询并行加速 | 一个查询拆给多个线程 | 单查询延迟、总 CPU 资源和协调成本 |

当前优先理解第一类。Quake 的 NUMA 查询内并行属于第二类，因此可借鉴数据放置与任务局部性思想，但实验口径不能直接混合。

### 6.2 建议对照

1. 一个节点内运行与跨节点运行，检查资源扩展行为。
2. 相同核心总数下使用不同节点分布，帮助分离核心数量与位置影响。
3. 集中分配、交错分配等共享索引布局。
4. 完整本地副本方案，记录额外内存、加载和复制时间。
5. 候选的部分复制或调度方案，在相同质量、线程与负载条件下比较。
6. 对关键模块分别关闭，确认收益机制。

报告同时给出总吞吐、线程/核心数量、单位核心表现和空间成本。不能把多用核心或多用内存得到的提升全部称为算法收益；扩展性比较与固定资源下的方法比较应分别展示。

### 6.3 指标和测量口径

- Recall@k、距离度量和精确近邻真值一致。
- 吞吐及 P50/P95 等延迟分布，说明是否包含排队、任务分发和结果合并。
- 说明负载是固定并发请求数，还是按固定到达速率持续提交。
- 实际线程位置、页面分布、迁移、节点负载与可能的内存带宽指标。
- 内存副本大小、峰值内存、初始化与额外查找成本。
- 查询分布改变时的退化与重复测量波动。

numastat 等内存分配统计不等于实际远端读取次数。硬件事件能否计数及其含义需逐机核对。应记录自动 NUMA 平衡、页面迁移、大页及其他关键系统条件，不能仅凭运行时间或分配位置认定全部瓶颈来自远端内存。

## 7. 硬件前提与本机能做什么

| 条件 | 为什么需要 |
| --- | --- |
| 至少两个可用且可区分的 NUMA 内存节点 | 真实比较本地、远端访问与多节点执行 |
| 每个节点足够的核心和内存 | 实现不同线程布局或容纳本地副本 |
| 可控制线程亲和性与内存分配 | 让方案与对照具有可解释的位置差异 |
| 可以观察页面分布和相关性能事件 | 建立机制证据 |
| 稳定的使用时段 | 减少其他用户对缓存、带宽和调度的干扰 |

后续需要向导师确认：CPU 型号、插槽数、操作系统可见 NUMA 节点数、每节点内存、可用核心、权限与资源使用方式。不能仅凭“服务器有很多核”认定能完成 NUMA 研究。

本机当天读到 Ryzen 7 7735H、8 核 16 线程、16 GB RAM、单个 16 MiB L3 实例；WSL2 可见约 7.4 GiB RAM。当前没有验证可用于本课题的多个 NUMA 内存节点，因此可用于代码开发和普通并发学习，不能据此给出跨 NUMA 节点优化的有效性结论。详细配置与基础计数器检查见 [Cache 文档第 7 节](HNSW_Cache优化方向与实验条件_2026-11-08.md#7-内存需求与硬件条件)。

讨论两个 NUMA 节点服务器只是帮助理解的假设，不代表学校硬件已经确认。

## 8. 与 Cache 方向如何比较

| 比较项 | Cache 访存与执行 | NUMA 数据放置与调度 |
| --- | --- | --- |
| 主要尺度 | 一次查询的数据访问、缓存利用和执行依赖 | 跨核心、缓存域、内存节点的资源组织 |
| 起步实验 | 单机、单线程即可 | 真实 NUMA 验证依赖合适服务器 |
| 主要修改 | 节点与字段布局、预取、搜索循环 | 分配、复制、线程组、队列、调度 |
| 主要风险 | 现有实现已优化，收益随负载和 CPU 变化 | 局部性与均衡冲突，副本空间和硬件依赖 |
| 当前进展 | 本机具备初步资源条件 | 先理解并阅读，服务器条件待确认 |

两者会交叉。拓扑感知调度可以改善缓存复用，节点数据重排也可能改变页面分布；后续论文需要明确主要研究尺度与贡献边界。

## 9. 为开题需要收窄什么

暂拟题目：“面向 NUMA 架构的 HNSW 并发查询数据放置与调度优化研究”。该题目当前仍偏宽，应根据真实瓶颈和方法缩小。

建议按以下顺序形成材料：

1. 先读 N1、N2、N3，分别区分分区扫描、CCD 调度和 CXL 近内存计算。
2. 获得学校服务器真实配置，判断实验能否实施。
3. 固定一个静态 HNSW 实现，建立线程与页面放置基线。
4. 比较共享索引与完整本地副本，判断复制或调度的潜在收益。
5. 在证据支持下，从选择性复制或调度等方案中选择一项主要问题。
6. 与导师确认相关工作差异、独立工作量和验收要求。

目前不预设加速比例，不承诺全面复制一定有效，也不将本文候选方案写成已经成立的创新点。当前状态仍是条件性候选方向。
