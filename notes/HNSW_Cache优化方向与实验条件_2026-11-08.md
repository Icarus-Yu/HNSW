## 2. HNSW 查询到底在做什么

向量检索的输入是查询向量，输出是按指定距离度量接近它的若干数据。向量可以来自文本、图像等，但检索内核实验可以直接使用现成向量数据集。当前不把文本向量化、模型训练或完整问答产品开发作为核心研究工作。

精确搜索可以计算查询与数据库全部向量的距离，再选出最近的 k 个。HNSW 使用多层近邻图，先从上层接近目标区域，再在底层展开搜索，通常只探索部分数据。图中的邻居是用于继续探索的连接节点，最终返回的查询近邻是检索目标，两者需要区分。[HNSW 原始论文](https://arxiv.org/abs/1603.09320)

底层查询可以简化为以下循环：

| 步骤 | 执行的工作 | 涉及的数据与开销 |
| --- | --- | --- |
| 选择候选 | 取出接下来探索的节点 | 候选集合、比较与队列操作 |
| 读取邻接表 | 获取当前节点的邻居编号 | 图结构读取 |
| 检查访问状态 | 判断哪些邻居已经处理 | 访问标记的分散读写 |
| 读取候选向量 | 获得距离计算所需的数据 | 向量读取与缓存行为 |
| 计算距离并更新 | 判断候选是否值得继续探索或保留 | 数值计算、分支、候选与结果维护 |
| 判断结束条件 | 继续探索或返回结果 | 搜索工作量与检索质量 |

后续需要读懂的代码集中在搜索循环及其使用的数据结构。以 hnswlib 为基线时，核心实现主要是 C++，Python 可以承担实验调度、数据整理和绘图。[hnswlib 官方仓库](https://github.com/nmslib/hnswlib)

## 3. Cache 优化涉及哪些基础概念

Cache 指 CPU 的硬件缓存，常见层级包括 L1、L2 和 L3。主内存 RAM 保存运行中的索引；SSD 保存文件或承担磁盘驻留查询的读取；GPU 显存属于另一种执行平台的数据空间。当前方向主要研究 CPU 与缓存、主内存之间的行为。

缓存按缓存行组织数据。以缓存行为 64 字节的机器为例，一行可以容纳 16 个 float32 数值；768 维 float32 向量占 3072 字节，理想对齐时覆盖 48 条缓存行。节点相邻并不意味着多个完整高维向量可以装进同一条缓存行。

| 概念 | 含义 | 可能的优化目标 |
| --- | --- | --- |
| 空间局部性 | 访问一份数据后，很快访问附近数据 | 让搬入的数据有更多部分被实际使用 |
| 时间局部性 | 同一数据在较短时间内再次使用 | 争取在数据被换出前完成复用 |
| 工作集 | 一段执行过程实际需要的数据集合 | 控制活跃数据量及其组织方式 |
| 缓存污染 | 搬入低价值数据，挤占仍有用的数据 | 避免过度预取、无效读取或不必要的数据混合 |
| 预取 | 提前请求可能使用的数据 | 减少需要使用数据时的等待 |
| 内存级并行 | 允许多个相互独立的内存请求重叠 | 隐藏部分访问延迟 |

硬件管理缓存装入和替换；软件主要通过布局、访问次序和预取提示影响行为。预取不是必然完成的保证，也不是越多越好。[Intel 优化手册](https://cdrdv2-public.intel.com/821612/248966-Optimization-Reference-Manual-V1-050.pdf)

需要区分两种瓶颈：一是访问存在依赖，CPU 等待数据而带宽尚未用满；二是需要搬运的数据量过大，接近可用带宽。二者可能需要不同手段。TLB 用于地址转换，其缺失与数据缓存缺失也不是同一个指标。

数据库总大小超过 L3，只能说明整个数据库放不进该缓存，不能据此证明查询受缓存缺失限制。实际还要看访问工作集、分布、数据维度和搜索工作量。

## 4. 现有实现已经做了什么

本次讨论检查的 hnswlib 源码已经包含以下机制：

- 底层节点记录使用连续的大块内存，记录中包括底层邻接信息、向量和标签。
- 查询循环中包含对访问标记、向量或后续节点数据的预取；是否启用取决于版本、平台和编译条件。
- 访问标记通过轮次标记复用数组，通常不需要每次查询清空整个数组。

连续分配不保证实际搜索相邻访问的节点编号也相邻。已有预取也不说明其目标与时机在所有负载下都最优。因此研究应定位现有安排的具体不足。

源码依据：[节点组织与搜索循环](https://github.com/nmslib/hnswlib/blob/master/hnswlib/hnswalg.h)、[访问标记池](https://github.com/nmslib/hnswlib/blob/master/hnswlib/visited_list_pool.h)。链接对应在线源码，后续实验应固定实际使用的提交版本、编译器和指令集设置。

## 5. 四类可能开展的工作

### 5.1 节点重排：调整不同节点的位置

问题：经常连续访问的节点，在内存里可能相距很远。可以根据图结构或访问关系，重新安排节点顺序。

实际工作包括：统计或分析访问关系、选择排序方法、搬移节点记录、重写内部编号和图引用、保留外部标签映射，再测量查询与预处理代价。

布局改变应尽量保持图连接、邻接表顺序和距离计算方式不变。需要检查映射、边关系、返回标签以及距离相同时的处理；不能只以程序能运行作为正确性证据。

2022 年图重排研究已比较多种排序方法，并研究访问统计引导的布局。因此“按热度排序”本身不能直接视为新贡献。后续可调查不同数据大小、向量维度、存储粒度及重排成本，但这些仍是候选问题。[2022 年正式版在线原文](https://papers.neurips.cc/paper_files/paper/2022/file/fb44a668c2d4bc984e9d6ca261262cbb-Paper-Conference.pdf)

若使用查询统计指导布局，应分开统计查询与评测查询，观察访问分布变化后的效果。

### 5.2 节点内部布局：调整字段和数组组织

问题：邻接信息、向量、标签和其他字段放在一起，还是分开存放，更适合实际访问模式？

可调查记录大小、字段拆分、对齐、空余空间，以及热点信息集中存储。修改可能涉及分配方式、节点地址计算和索引保存加载。

需要比较的不是“哪种形式看起来更紧凑”，而是其是否减少有用路径上的读取和等待。拆分也可能增加间接寻址；填充和对齐可能增加总空间。不同节点尺寸下的收益需要实验确认。

### 5.3 预取与执行协同：调整提前读取的目标与时机

问题：邻居编号已知之后，能否让候选数据请求与当前计算更好地重叠？

| 设计选择 | 需要验证的问题 |
| --- | --- |
| 提前读取哪个对象 | 向量、访问标记还是邻接信息，哪部分值得提前请求？ |
| 提前多少个候选 | 太晚可能来不及，太早可能被换出 |
| 是否先检查已访问状态 | 能否减少无效向量预取，又是否推迟请求？ |
| 一次处理多少邻居 | 批量组织的好处能否覆盖临时空间和管理成本？ |

应以现有预取版本作为重要对照。批量计算距离与推迟候选集合更新是不同改动；若改变展开顺序或更新时机，可能改变搜索路径、计算次数和召回质量，需分别验证。

### 5.4 辅助结构：访问标记与候选集合

问题：访问标记和候选维护是否在某些规模、维度或搜索设置下构成明显开销？

可调查标记表示的空间、随机读写、复用方式，以及候选集合的存储和更新成本。更紧凑的表示也可能增加清理、寻址或比较成本。应先确认热点占比，再决定是否值得作为主要研究对象。

查询交错、共享缓存竞争等可作为后续扩展；当前建议先把单线程查询中的一项问题研究清楚。

## 6. 实验如何设计

### 6.1 基本范围

建议从单机、单线程、静态内存索引开始，在同一 CPU 上比较原始版与改进版。之后可补充单机多查询并发，或在另一台 CPU 上分别报告可迁移性结果。

实验应记录代码版本、索引构建设置、数据类型、距离度量、编译器、优化选项、线程数、供电和负载条件。若能保持同一图结构，尽量复用索引，避免把构建差异混入查询实现差异。

### 6.2 质量与性能指标

Recall@k 使用对应数据库上的精确近邻真值。例如真实最近的 10 条数据找回 9 条，则该查询的 Recall@10 为 90%。截取数据库子集后，原真值不一定仍适用，需要核对或重新计算。

| 指标 | 用途与注意点 |
| --- | --- |
| Recall@k | 检查检索质量；不能以牺牲质量得到的速度直接证明实现优化 |
| 查询延迟及 P50/P95 | 检查典型和较慢查询；记录采样与计时方式 |
| QPS | 多查询负载下的吞吐；固定线程数与负载口径 |
| 搜索工作量 | 距离计算、节点展开等；检查速度变化是否来自搜索工作量改变 |
| 缓存与内存事件 | 辅助解释机制；核对事件定义、权限和硬件支持 |
| 空间与预处理 | 索引空间、峰值内存、构建、重排或额外准备时间 |
| 波动 | 重复测量，报告稳定性和退化条件 |

主要比较召回率—延迟曲线，而非只固定一个搜索参数。hnswlib 的 ef 控制搜索范围与质量、时间之间的权衡，且不得低于 k。[参数说明](https://github.com/nmslib/hnswlib/blob/master/ALGO_PARAMS.md)

单个缓存缺失率不能独立证明瓶颈。性能分析采样、访问轨迹记录和正式计时宜分开进行，避免重度插桩改变被测程序行为。需要区分正常稳定运行、首次运行和人为冷缓存实验，不把反复清空缓存当作所有负载的默认模型。[内存访问分析参考](https://www.intel.com/content/www/us/en/docs/vtune-profiler/user-guide/2023-1/memory-access-analysis.html)

### 6.3 数据数量级和实验数量

| 阶段 | 数据库向量数量 | 目的 |
| --- | --- | --- |
| 学习、调试 | 1 万至 10 万 | 读懂流程、检查实现 |
| 首轮基线 | 100 万左右 | 建立质量—性能曲线和瓶颈证据 |
| 正式扩展 | 100 万至 1000 万 | 检查规模适用性，视资源安排 |
| 更大规模 | 条件允许时补充 | 不是当前启动研究的前提 |

可先按每组约 1 万条查询、重复 3–5 轮规划，之后按统计目标和波动调整。不同真实数据集的维度与分布可能同时不同，不能把跨数据集差异全部归因于维度。

实验数量示例：2 个数据集 × 2 个规模 × 2 个版本 × 5 档搜索参数 × 5 轮重复 = 200 组运行；若每组 1 万条查询，合计约 200 万次查询执行。该示例不构成耗时承诺，构建索引、真值准备和重排可能额外花费较多时间。

## 7. 内存需求与硬件条件

原始 float32 向量空间 = 向量数量 × 维度 × 4 字节。下表用十进制 MB、GB，仅含一份向量。

| 数量 | 128 维 | 768 维 |
| --- | --- | --- |
| 10 万 | 51.2 MB | 307.2 MB |
| 100 万 | 512 MB | 3.072 GB |
| 1000 万 | 5.12 GB | 30.72 GB |
| 1 亿 | 51.2 GB | 307.2 GB |

实际还包括图结构、标签、访问状态、查询、真值、输入副本和临时缓冲。例：1000 万条 768 维向量若同时保留输入与索引中的两份向量，仅向量就约 61.44 GB，64 GB RAM 可能不足。实际峰值与加载、构建和重排方式有关。

当前资源规划建议：开发可从 16–32 GB RAM 起步；正式实验争取 64 GB；千万级高维或需要大缓冲的实验可考虑 128 GB。GPU、多插槽和多个 NUMA 节点均不是 Cache 方向起步的前提。重点是稳定 CPU、足够内存、可用分析工具和较少干扰的实验时段。

### 7.2 对本机的规模判断

| 数据规模 | 当前判断 |
| --- | --- |
| 10 万条、128 维 | 适合学习和调试 |

笔记本计时应记录插电状态、功耗模式、温度和后台负载；单线程实验尽量使用稳定的物理核心，减少其同核逻辑线程和共享缓存竞争。WSL 可用于初步研究，后续可在学校原生 Linux 服务器复核机制与规模适用性。

### 8.1 方向 A 的近期核心参考：VSAG

当前优先精读 VSAG，保留 2022 图重排为基础。VSAG 的访存研究与 CPU 图检索对象相近，有 2025 正式版本及 [公开实现](https://github.com/antgroup/vsag)。相较之下，KBest 的 ARM 平台结论需额外核对适用性，SymphonyQG 的量化图协同超出当前主线边界。

阅读重点是 [正式原文第 3 节](https://www.vldb.org/pvldb/vol18/p5017-cheng.pdf)：软件预取、有效访问组织、步长与深度、部分冗余存储。结合第 4 节了解哪些参数已经被调优，第 6.4 节检查消融证据。论文同时包含量化与其他模块，系统整体加速不能解释为纯缓存优化收益。

本次选定的是核心参考，尚未固定优化方法或完成复现。后续应核对论文对应的代码版本与构建条件，并将原始实现、文献中可复现的相关方法、本人候选改动分别比较。若采用 hnswlib 作为起步基线，需要说明与 VSAG 的表示、图结构、参数和执行差异；不能仅比较两个系统总速度后就归因于某项预取改动。

需要特别对照的已有内容：VSAG 已考虑先识别有效邻居再预取、预取步长与深度，以及冗余布局的资源权衡。因此“只预取未访问节点”“调预取距离”“复制邻居以便连续读取”都不能直接标成新方法。

精读后需要形成的材料：

1. 列出第 3 节各方法具体改变的数据结构与搜索步骤。
2. 对照固定版本的 hnswlib，确认哪些安排已有、哪些不同。
3. 选择可以独立测试的一项机制，先比较正确性、搜索工作量和相同质量下的代价。
4. 将不同维度、搜索范围、工作集与 CPU 条件作为待调查因素；这些因素本身不等于新的贡献。

### 8.3 现有数量是否足够

最初四篇材料适合入门，但包含旧基础文献、跨平台系统和量化相邻研究，用于完整说明当前 A 方向仍有覆盖缺口。本次补齐近期核心、方法评测和搜索质量控制，是第一轮扩充，不代表相关工作检索已经完成。

后续围绕选定的具体问题，继续追踪核心论文的参考文献与后续工作，形成“瓶颈—已有方法—实现变化—质量影响—成本—适用条件”对照表。是否足够应由关键方法是否覆盖、与候选贡献能否清楚区分及学校要求判断；不预设一个通用篇数门槛，也不以下载数量代替精读。

## 9. 为开题准备什么

| 下一项工作 | 应形成的材料 |
| --- | --- |
| 读懂一次底层查询 | 能解释数据结构、访问步骤和依赖关系的说明 |
| 梳理直接相关方法 | 方法改变哪一层、适用条件、与候选方案重合点的对照表 |
| 建立本机基线 | 数据、真值、版本、参数和重复测量记录 |
| 定位一项瓶颈 | 结合热点与多种证据的瓶颈假设 |
| 收窄核心方法 | 一项可实现、可对照、可解释的改进方案 |
| 与导师确认 | 独立贡献形式、工作量、服务器资源和验收要求 |

暂拟题目可保留为“面向 CPU 的 HNSW 查询访存与执行优化研究”或“HNSW 图近邻搜索的访存行为分析与优化”。在具体方法确定前，不把“自适应”“新型”或固定加速比例写入题目、目标或贡献。

当前建议是先在本机以百万级、128 维、单线程查询建立研究流程，再决定布局路线还是执行路线。该建议不是已经确认的优化方法，相关工具配置、数据准备和实验尚待开展。
